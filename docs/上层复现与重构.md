# 上层复现与重构

## 学生刷好四块板之后

| 步骤 | 学生完成的事 | 可以观察的结果 |
| --- | --- | --- |
| 1　读通信 | 读取 J1～J4 的 CAN FD 状态和固件版本，认清每块板的机械轴 | 看到四个独立节点的电压、电角标定和编码器状态。J1 是丝杆，J2 是大臂，J3 驱动小臂，J4 是末端旋转 |
| 2　认机械参考 | 新板用 `13-electrical` 完成各自电角标定并保存。实物对准已知标记后用 `14-reference` 接续机械参考，逐轴验证正方向和反馈 | 关节角随实物一致，重启后的参考有明确接续依据。丝杆吸取、释放与运输层均有实测高度 |
| 3　看清棋盘 | 启动相机，取得 1280 × 720 原图，依次手写取帧、准备输入、RKNN 推理、解码与绘图 | 同一盘面能看清棋子身份与位置，显示缩放和推理 ROI 各自独立 |
| 4　把格点变成毫米 | 固定棋盘，用吸头圆心对准 (9,0)、(9,8)、(0,0) 的印刷交点，记录同一组原图像素和 J2/J3 角。再记录 J1 工作层、观察位、弃子点 | `15-site` 用正式正运动学求三点，生成这台机器的现场记录。用中心和靠边的独立交点核对实际吸头。R10 提供基准，格距取实物印线 |
| 5　分开核对定位与吸放 | 先空吸头定位，再用一枚棋子从指定格开始逐格取放。横移前垂直抬至搬运层 | 得到 90 格真实反馈和观察结果。吸取时正向通电并保持，放子在目的高度关断 |
| 6　走出一手合法棋 | 在 C++ 模拟局面中先下普通一步，再下吃子的一步。接 Pikafish 及同版本 NNUE | 引擎收到起始 FEN 和完整已确认历史，返回合法走法或应手。吃子时先取被吃子，移出棋盘关断，再搬进攻子 |
| 7　走完整局 | 开面板，确认开局后选择两个数字格点。程序执行人走的一步和引擎应手 | 每步回观察位，重新看到预期盘面才写入棋谱并换边。验收同时覆盖中部、边缘、吃子和中途恢复 |

首次安装完成后，日常开局跳到第 7 步。通信与设备启动重新核对当前状态。重装基座、挪动棋盘或改变棋面高度时，重做所影响的示教。90 点测试用于安装验收及排查。

## 课堂代码怎么写

写法以用户指定的 GitHub `bms` 工程为参考。按正常调用顺序读入口、数据和结果。[教师版 BMS 对照与课堂代码写作规范](课堂代码写作规范.md)

1. 棋盘上的位置一律写成 `[行][列]`。第 0 行是黑方底线，第 9 行是红方底线，从红方看最左边是第 0 列。识别结果、棋局和机械目标都能用同一对下标查到。变量名区别像素、毫米和关节角。
2. 一手棋从头到尾传同一个 `Move`。例如红兵前进一步，起点是 `(6,0)`，终点是 `(5,0)`。引擎协议和兼容棋谱把这一步写成 `a3a4`。视觉归格、查表和取放直接用行列。
3. 看一手棋就按动作顺序读。先确认起点和终点，再生成取放动作。回到观察位，看见预期盘面，才换边。一个判断放在能决定下一步的位置。同一盘面已经确认时，直接往下走。
4. 一行写清一步。能从名字读懂的赋值直接写，注释解释单位、坐标方向或动作先后的原因。自审时挑一手普通走法和一手吃子，从输入跟到实物目标，把中途多出来的格式转换、转发函数和重复判断删掉。

例如红兵从 `(6,0)` 到 `(5,0)`，面板收到的合法走法项是 `[[6,0],[5,0]]`。上位机从进程管道收到 `legal_rc`，刷新网页会读到面板内存中的最新一手。

从 `Match_turn` 顺读一手棋。先查合法走法，再由 `selectMove` 写出一个 `Move` 和是否需要机械臂代走。玩家亲手在盘上走棋时，用 `inferMove` 找出唯一能得到实盘的合法走法。面板或引擎选棋才进入 `carry`。两条路最后都在确认实盘后记谱。[对局源码](../app/game.cpp)

读吃子时，`carry` 先在盘面副本推演一步，留下核盘用的预期结果，再按执行顺序排动作。先取走目标格被吃的棋子，送到盘外，再把进攻子从起点搬到目标格，最后回观察位核盘。设备中断后先确认停车、回观察位并看到原局面，再重试同一张动作表。取子、落子、盘外弃子的高度和磁铁动作各按顺序写明。[动作规划](../motion/plan.cpp)

## 固定棋盘的几何按三步读

1. `Geometry_calibrate(redLeft, redRight, blackLeft, board)` 接收红左、红右、黑左三个交点各自的像素和基座毫米。横向一格等于红方底线两端之差除以 8，纵向一格等于红左与黑左之差除以 9。按行、列填满 `board.cell` 的 90 个点。
2. `Geometry_assign` 取这一帧每个检测框的中心，反算行列并就近归到交点，把棋子身份填入棋盘。放棋使用同一格的 `.xy`。
3. `Geometry_draw` 把同一格的 `.pixel` 画到原图。三帧确认在对局的 `observe` 中进行。[几何源码](../vision/geometry.cpp)

固定后的现场依次做三个交点、Z 工作高度、空吸头 90 点。实测表从 `15-site.cmd --template` 生成。装配图、实际取点和命令见 [R13 装配与标定](cad/R13装配与标定.md)。

## 每层实际接收与交付的数据

| 职责 | 输入 → 输出 | 核心实现 |
| --- | --- | --- |
| 入口与会话 | 本机测量、玩家侧、模型 → 一个会话 → 确认初始盘或已保存的局面 → 逐手走棋 | [主程序](../app/game.cpp)、[会话类型](../app/game.hpp) |
| 设备与现场初始化 | TOML 分区中的机械参数、标定和对局设置 → 本次会话 | [安装示例](../config/installation.toml) · [读取入口](../app/site.cpp) |
| 取流和识别 | BGR 帧 → 固定 ROI 的 RGB 输入 → 三个 NPU 输出 → 类别、框、分数 | [取帧](../vision/capture.cpp)、[YOLO](../vision/yolo.cpp) |
| 格点 | 三组像素与毫米 → 90 个固定目标；检测中心 → 数字行列与连续稳定的盘面 | [几何](../vision/geometry.cpp) |
| 棋局 | 10×9 棋子数组、行棋方、已确认历史 → 一手候选棋及预期盘面 | [棋局](../chess/board.cpp)。字符是引擎棋子编码，大写红、小写黑；空格为 `.` |
| 棋力 | 起始 FEN、历史、思考时间 → 合法走法与最佳走法 | [Pikafish](../chess/pikafish.cpp)。每回合发一次起始局面与棋谱，先取合法表，轮到电脑时继续在该局面搜索。UCI 格号只用于协议或兼容棋谱 |
| 回合 | 玩家选择或引擎选择 → 验证走法 → 普通搬子/先弃子再搬子 → 核盘、提交或恢复 | [对局](../app/game.cpp)。计划中的一步保持 pending，实物确认后才更新历史 |
| 运动 | 数字格点 → 基座 XY → 关节目标 → 有序的运动、吸合、关断 | [规划](../motion/plan.cpp)、[执行](../motion/execute.cpp)。J4 在正常下棋中保持原姿态 |
| 显示和测试 | `Session` 把盘面和棋谱交给显示端。需要双画面的台架在接入层生成 JPEG。测试端读取动作与最终盘面 | [会话接口](../app/game.hpp)、[上位机](../tools/match_panel.py) |

正式 C++ 使用 `pickupDeg`、`travelDeg`、`releaseDeg` 等有单位的数值。对局运行时的外部算法资源是 RKNN 模型、Pikafish 可执行文件及 NNUE 权重。本机安装表随程序编译，中文棋名直接交给 OpenCV 5 的内置字体 uni。独立测量与回放工具可以显式读取历史夹具。

上位机的“相机双画面”从内存接收最新的 JPEG。Linux 上单独运行 `run-vision.sh` 时，识别图像作为连续 JPEG 写到标准输出，可以直接接 `ffplay -f mjpeg -i pipe:0`。面板进程退出后，本局内存棋谱随之释放。

## 下一轮重构的验收边界

1. 逐模块读源码，先确认数字行列、棋子编码、走法历史与 UCI 的边界，然后审阅回合和恢复。安装流程与日常主循环分开。
2. 原生 C++ 真实驱动仍须实现状态读取、整组运动、磁铁正向/关断及停稳确认。v3 接受成段绝对目标，基于同一姿态的肘形选择与 J2/J3 到位 HOLD 已在 Windows 台架实现。原生后端须匹配板端实际指令语义后上机验收。
3. 对误停按现场状态帧区分命令拒收、通信失联、编码器、电流、母线和轨迹故障。用可复现工况消除误触发。此次发布的构建仍包含故障处理，学生发布版还需四轴整机验证。
4. 以固定后的实物走完安装流程、单步、吃子和一局完整人机对弈。记录实际板端版本、标定、录像和落点后再冻结教材中的参数与操作截图。
