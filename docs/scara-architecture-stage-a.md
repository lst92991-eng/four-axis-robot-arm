## 结论与决策

1. **一手棋最难读的地方是状态含义交叉。** `Match_turn` 的顺序已经清楚。深读时会遇到 `carry` 同时构建计划、执行、核盘、等待人工、停车回位与重试，`observed.valid` 先表示本帧可归格再表示三帧稳定，`reportBoard` 还会改写观察盘。优先收敛这三处分工。[app/game.cpp:116](https://github.com/lst92991-eng/four-axis-robot-arm/blob/89f93e854ae4d4d9c9c6d34bba9239fb9ad47547/app/game.cpp#L116) · [app/game.cpp:193](https://github.com/lst92991-eng/four-axis-robot-arm/blob/89f93e854ae4d4d9c9c6d34bba9239fb9ad47547/app/game.cpp#L193) · [app/game.cpp:281](https://github.com/lst92991-eng/four-axis-robot-arm/blob/89f93e854ae4d4d9c9c6d34bba9239fb9ad47547/app/game.cpp#L281)
2. **有两处能直接消除计算。** 吃子时目的格先取被吃子、后放进攻子，用同一标定与臂参做了两次相同逆解。手走识别则对每条候选复制并比较整盘。前者按格求解一次，后者先看真实盘面的两格差分，再查合法表。[app/game.cpp:209](https://github.com/lst92991-eng/four-axis-robot-arm/blob/89f93e854ae4d4d9c9c6d34bba9239fb9ad47547/app/game.cpp#L209) · [motion/plan.cpp:27](https://github.com/lst92991-eng/four-axis-robot-arm/blob/89f93e854ae4d4d9c9c6d34bba9239fb9ad47547/motion/plan.cpp#L27) · [chess/board.cpp:134](https://github.com/lst92991-eng/four-axis-robot-arm/blob/89f93e854ae4d4d9c9c6d34bba9239fb9ad47547/chess/board.cpp#L134)
3. **动作表仍然有业务价值。** 执行前能核对整手，Windows 台架能用实际姿态预走 CAD 路线。教学层的轴选项事实上只有全姿态及单独升 Z，建议用这两种明确意图表达。台架协议中的动作编号、轴掩码和单位在接缝映射，保留盘外释放标识。[app/game.cpp:370](https://github.com/lst92991-eng/four-axis-robot-arm/blob/89f93e854ae4d4d9c9c6d34bba9239fb9ad47547/app/game.cpp#L370) · [bench/field/usb_io.cpp:308](https://github.com/lst92991-eng/four-axis-robot-arm/blob/89f93e854ae4d4d9c9c6d34bba9239fb9ad47547/bench/field/usb_io.cpp#L308) · [bench/field/run_game.py:613](https://github.com/lst92991-eng/four-axis-robot-arm/blob/89f93e854ae4d4d9c9c6d34bba9239fb9ad47547/bench/field/run_game.py#L613)

## 一局、一手、一次观察的现有数据流

```text
TOML → 安装值和固定90格 → Match_run → Runtime_open
  → 等待开局许可、关磁铁、升Z、回观察位
  → 看三帧 → 操作员确认 → 再看新三帧 → 建立或接续棋局
  → 逐手读取引擎合法表和应手 → 判终局 → 确定走法
       亲手走：看新盘 → 推断合法走法 ─────────────────┐
       代走：再看原盘 → 查XY和逆解 → 生成整手动作表    │
            → 执行并回观察位 → 看新盘确认目标 ──────────┤
       两条路汇合 → Game_commit → 刷新显示 → 下一手 ←───┘
  → 统一收尾，报告停止是否确认

目标检测的原图框与帧 ID → 单帧归格 → 有效且不同的新帧
  → 连续三帧同盘 → 输出稳定盘 → 开局确认、推断手走或核对落点
```

`Match_run` 有两条真实的代码接续。Windows 的动作经过 C++ DLL 和 Python 台架，依据设备反馈预检 CAD 路线，横移前升到全搬运层，之后核对吸放高度、控制磁铁并按段执行。仿真替身调用 C++ 五次轨迹执行器。Linux 原生程序也调用该执行器，但本提交的四个 `Drive_*` 入口仍返回失败。实机教案从 Windows 台架解释可运行行为。[bench/field/usb_io.cpp:308](https://github.com/lst92991-eng/four-axis-robot-arm/blob/89f93e854ae4d4d9c9c6d34bba9239fb9ad47547/bench/field/usb_io.cpp#L308) · [bench/field/run_game.py:588](https://github.com/lst92991-eng/four-axis-robot-arm/blob/89f93e854ae4d4d9c9c6d34bba9239fb9ad47547/bench/field/run_game.py#L588) · [tests/game_sim_io.cpp:245](https://github.com/lst92991-eng/four-axis-robot-arm/blob/89f93e854ae4d4d9c9c6d34bba9239fb9ad47547/tests/game_sim_io.cpp#L245) · [app/rv1106.cpp:125](https://github.com/lst92991-eng/four-axis-robot-arm/blob/89f93e854ae4d4d9c9c6d34bba9239fb9ad47547/app/rv1106.cpp#L125)

### 现有复杂度来源图

```text
Session
 ├─ 已确认棋局、历史、行棋方 ──► 引擎、裁定、记谱
 ├─ legal ──────────────────────► 判终局、选棋、面板高亮
 ├─ observed.board + valid + 帧号
 │     ▲ 归格写本帧有效 ──► observe 改写成三帧稳定
 │     └ reportBoard 为显示问号又改写盘面
 └─ pending ────────────────────► 面板、异常退出、续局保护

carry
 ├─ 查原盘 → 建预期盘 → 求解、排步骤
 └─ completed × pending × 停止请求 × 核盘结果
      ├─ 目标盘 → 提交
      ├─ 落错 → 人工确认 → 看目标或原盘 → 确认或重新执行
      └─ 驱动失败 → 人工恢复 → 确认停稳 → 回观察位 → 核对原盘 → 重试

PickStep 通用载荷 → C++ 执行读取轴掩码/持续时间
                 → Windows 适配器再解包并按全高/路径约束执行
```

复杂度有三个来源。第一是同一变量在不同阶段换含义。第二是单个函数同时持有真实设备状态、预期棋局和重试协议。第三是协议字段进入教学路径。保留那些有消费者的数据，诊断显示在输出边界生成。面板只在 `wait_human` 时导出 `legal`，而 Windows 的 `purpose == "prepare"` 会改变回观察位和磁铁高度处理，有直接的实机语义。[app/game.hpp:12](https://github.com/lst92991-eng/four-axis-robot-arm/blob/89f93e854ae4d4d9c9c6d34bba9239fb9ad47547/app/game.hpp#L12) · [bench/field/usb_io.cpp:268](https://github.com/lst92991-eng/four-axis-robot-arm/blob/89f93e854ae4d4d9c9c6d34bba9239fb9ad47547/bench/field/usb_io.cpp#L268) · [bench/field/run_game.py:611](https://github.com/lst92991-eng/four-axis-robot-arm/blob/89f93e854ae4d4d9c9c6d34bba9239fb9ad47547/bench/field/run_game.py#L611)

## 建议的新组织

| 保留或收敛的业务入口 | 明确的输入和输出 | 净收益与边界 |
| --- | --- | --- |
| `Match_run / Match_start` | 安装配置、已接续棋局 → 设备开启与确认开局 → 总收尾 | 保留回车前后独立的新帧观察，集中处置资源失败和停止回执 |
| `Match_turn` | 当前棋局、合法表 → 选定走法 → 已完成才 `Game_commit` | 保留一眼可查的记谱点。引擎应手一次核对。人工模式的重试只在人工输入里发生 |
| `Plan_turn` 或现有规划入口的等价扩展 | 走法、原盘面、固定格点与示教 → 完整动作表 | 一手最多解起点、终点、弃子点各一次，规划成立之前执行端得不到半手。由该入口消化原 `carry` 的规划职责 |
| 搬棋执行与核对 | 已排好的整手、原盘和目标盘 → 已确认、原盘可重试、结束 | 实机分段协议仍由适配器处理。保留运动失败通道及位置核对通道，让两种恢复各自有一个决定重试的位置 |
| `observe` | 帧号、检测框、固定标定 → 可用于决策的稳定盘 | 每帧结果用局部量，三帧状态统一在这一步持有，显示提示用只读盘面视图。相机接入继续处理传输与重连边界 |
| `inferMove` | 原盘、稳定盘、已验证合法表 → 一手或无需提交 | 一次盘面差分，确认两格与棋子身份和合法表。若区分无变化与非法，撤销选棋层另一次整盘相等判断 |

一手代走只需看原盘、定走法目标、求整手计划、执行、看结果、提交。函数列表以上表为候选。审批后按最少新增接口实现。语义进入另一函数时，必须随输入传入明确数据并交还可检验的结果。若仍强调靠全局状态、持有等量独立分支或重复求解，则该拆分没有验收价值。

### 三种核盘条件

| 发生点 | 原盘 | 目标盘 | 其他盘面或坏帧 |
| --- | --- | --- | --- |
| 机械动作前 | 可继续计划 | 无特殊意义 | 提示恢复，等新鲜稳定原盘后才发动作 |
| 动作已完成后 | 仅在人工确认后重新观察到原盘才可重试 | 仅在新鲜稳定观测吻合后提交 | 提示差异，人工确认后重新看盘 |
| 驱动失败后 | 人工处理并确认停机、回观察位后再次观测原盘才放行 | 当前故障恢复协议仍要求原盘 | 维持待确认状态，退出也只保存已确认棋谱 |

将报错后的 `pending` 当作动作是否已发而结果尚未确认的上位机状态。运动结束、停车确认和棋盘已证实是三件事。当前 `Runtime_close` 中的视觉资源关闭和停车在一个 `try` 内先后调用，前者抛出时可能跳过随后设备关闭。C++ `Motion_stop` 同样需要确认关磁抛错时另一条停车仍可尝试。此处是静态审查发现的异常路径风险，建议列为单独批准和故障注入验证的安全修复项。[bench/field/usb_io.cpp:85](https://github.com/lst92991-eng/four-axis-robot-arm/blob/89f93e854ae4d4d9c9c6d34bba9239fb9ad47547/bench/field/usb_io.cpp#L85) · [motion/execute.cpp:53](https://github.com/lst92991-eng/four-axis-robot-arm/blob/89f93e854ae4d4d9c9c6d34bba9239fb9ad47547/motion/execute.cpp#L53) · [app/game.cpp:220](https://github.com/lst92991-eng/four-axis-robot-arm/blob/89f93e854ae4d4d9c9c6d34bba9239fb9ad47547/app/game.cpp#L220)

## 逐函数审查计数口径

状态数按为了继续业务或判断结果必须同时理解的可变状态组估计。数组、盘面、运行状态、计时窗口各算一个组，轮次索引和自由临时值另作说明。外部依赖注明但不强行计作每个函数的持久状态。该计数用于复查依赖是否变少。

## 算法与数据必要性

| 算法或载体 | 当前问题与保留的能力 | 更直接的候选和删除代价 |
| --- | --- | --- |
| 正逆解及肘形 | 示教参考及转向决定驱动角与基座毫米，检查不可达及同侧肘 | 删除同一点重复计算。几何可达仍需 Windows 实际姿态与 CAD 换肘约束 |
| 五次轨迹 | 按速度、加速度上限同步三轴，端点可静止 | 保留起点、终点、时长及纯采样函数。用别的曲线会改变验收结果。停稳由反馈确认 |
| 三点双平面和坐标修正 | 原图找格，基座运动，实际机位含非零机械补偿 | 一次建表、一次应用补偿。Windows 归格与盘外过滤的重复投影可合并，须保证两阈值、预览协议及坏帧语义 |
| 连续帧观察 | 避免一帧遮挡误判和重复帧虚增计数 | 一处保留候选盘、相邻帧 ID 与计数，日志节拍单列。删除任一稳定判据会失去验过的拒绝能力 |

| 引擎、重复和接续 | 起始 FEN 完整历史、协议校验、同一行棋方裁定 | 可信边界后减少重复格式检查，重复仍直扫有界历史。不能用空表伪装失败或用有碰撞的摘要代替盘面 |

## 下一阶段优先级与独立验收

- **P0 · 冻结接口与风险用例。** 以 89f93e8 独立构建对照。将视觉关闭失败时仍尝试停车、停车未确认且连接释放仍闭锁、引擎坏结构不判负分列为审批项。当前 Windows 失败处理会保存停稳结果并释放总线。若未确认，后续 stop 只能读缓存的失败，回车本身无法取得新证据。[台架异常与停止](https://github.com/lst92991-eng/four-axis-robot-arm/blob/89f93e854ae4d4d9c9c6d34bba9239fb9ad47547/bench/field/run_game.py#L665)
- **P1 · 删除重复计算。** 单次差分识别手走，整手规划中同一点只做一次逆解。对照 90 格双平面、可达和同肘形解、普通及吃子动作与报错前零下发。报告每手真实逆解次数和每次识别实际扫描的整盘次数。
- **P1 · 取消共享状态双义。** 本帧可用、稳定盘和显示投影分别交付。明确 carry 的核对/重试/退出，并重跑开局确认中盘面变化、思考后实际换子、坏帧和重复帧、设备故障、人工复原、人工修到目标后直接提交、取消后保留确认棋谱及 pending。面板 phase、frame_id、legal_rc 和未知格是验收合同。[基线对局回归](https://github.com/lst92991-eng/four-axis-robot-arm/blob/89f93e854ae4d4d9c9c6d34bba9239fb9ad47547/tests/run_match_program.py#L128) · [帧号回归](https://github.com/lst92991-eng/four-axis-robot-arm/blob/89f93e854ae4d4d9c9c6d34bba9239fb9ad47547/tests/run_match_program.py#L289)
- **P2 · 课堂动作限域。** 只在旧适配合同可由一个接缝保持时改变动作表表示。对照六字段动作载荷、取放先后、只升 Z、盘外释放标记、CAD 途经点、磁铁高度与应答。若需同时维护两套课堂动作模型，则保留现有动作表及执行表达。
- **P3 · 执行器细化。** 同一时钟和反馈序列下逐样本比较三轴参考位置/速度、时长和边界。对照无移动、同步、限幅、250ms 稳定窗口扰动后重计、反馈中断和取消后不发额外动作。已有报告核对 61 次终点及样本数，仍需逐样本独立基准。[轨迹限幅测试](https://github.com/lst92991-eng/four-axis-robot-arm/blob/89f93e854ae4d4d9c9c6d34bba9239fb9ad47547/tests/motion_plan_test.cpp#L113) · [驱动替身故障测试](https://github.com/lst92991-eng/four-axis-robot-arm/blob/89f93e854ae4d4d9c9c6d34bba9239fb9ad47547/tests/motion_backend_test.cpp#L83)
