# SCARA 象棋视觉坐标对接

2026-11-06。本轮代码使用 C++17、OpenCV **5.0.0**，只做几何计算、离线检查和数据输出，不连接 CAN，不使能、回零或移动机械臂。按用户给定条件，关节参考位置有效；本模块不重新建立关节参考。

## 两层映射

1. `PlaneMap::pixelToBase`：原相机图像经一致去畸变处理后的像素 → 基座 XY，单位 mm。首次用实际对应点建立，独立点验证通过后保存。
2. `Board::gridToPixel`：棋盘 `(column,row)` → 同一像素坐标。棋盘平移、旋转后仅重新定位这一层。

目标计算等价于 `normalize(pixelToBase * gridToPixel * [column,row,1])`，normalize 表示除以最后一维。相机相对基座、图像几何和棋盘平面高度不变时，不需要随棋盘移动重新标定第一层，也不需要机械臂重新对准棋盘四角。

棋盘编号为 `column=0..8, row=0..9`；原点是红方视角左下交点，列向红方视角右侧增加，行向黑方增加。数组索引 `row*9+column`。物理尺度来自首次像素与基座毫米坐标的对应关系，不依赖猜测格距。

## 构建

```sh
cmake -S . -B build-geometry -DOpenCV_DIR="包含OpenCVConfig.cmake的目录" -DCMAKE_BUILD_TYPE=Release
cmake --build build-geometry --config Release
ctest --test-dir build-geometry -C Release --output-on-failure
```

依赖 `core,imgproc,imgcodecs,geometry,calib`，没有 ArUco 或 contrib 依赖。OpenCV 5 的几何与标定模块已经拆分，新代码使用对应头文件；见 [OpenCV 5 迁移说明](https://github.com/opencv/opencv/wiki/OpenCV-4-to-5-migration)。

本机已使用 Visual Studio 2026 / MSVC 与官方 Windows x64 OpenCV 5.0.0 SDK 构建。可执行文件在 `build-geometry/`；Windows `opencv_world500.dll` 自动复制到同目录。SDK 存于用户缓存，不纳入项目源码。Windows 程序不是 RV1106 程序；板端需要用匹配当前 uClibc 镜像的 ARM 工具链和 OpenCV 5.0.0 重新构建，本轮未进行 ARM 实机部署。

## 首次平面标定

复制并填写 `config/vision/calibration.example.yml`：

- `pixel` 是**原始采集帧**上的 `(u,v)`，不是浏览器缩放后的坐标，也不是 YOLO 的 640 输入坐标。
- `base_xy` 是同一物理平面点对应的实际 TCP 基座 XY，单位 mm。关节参考有效不等于可以忽略 FK 尺寸和 TCP 偏置；坐标来源需要可靠。
- 标定时观察棋盘平面上的点。不要将高出平面的工具顶部、棋子顶面或指示贴纸位置与棋盘平面的 XY 混用。
- 推荐 6 个拟合点＋3 个独立检查点。数学上允许至少 4 个非共线拟合点，但必须另有至少 3 个不同的检查点。点无需选棋盘四角，应在可达、预期操作区域内尽量分散。
- 填写真正的 `plane_z_mm` 和 `allowed_error_mm`；模板中的 NaN 会被拒绝。允许误差按棋子、吸头及机械误差预算确定，代码不擅自指定现场阈值。
- 已有相机内参时填入 `K`、`distortion`，标定点、格线和检测中心均使用同一去畸变像素体系（P=K）。没有内参时允许先拟合 raw-pixel 近似，但仍须通过独立毫米误差验证；单应性不能消除径向畸变。

```sh
scara_geometry_tool calibrate measured-pairs.yml plane-map.yml
```

程序报告拟合/检查 RMS、最大值和逐检查点误差。失败时不保存可用矩阵；成功保存矩阵、相机配置、平面高度、容差、原始对应点和误差。加载时重新计算并核验，不盲信 `valid` 标志或文件中被改动的矩阵。

运行目标限定在拟合点凸包覆盖区内。首次应覆盖预计的棋盘移动范围；移出已验证区域时返回无效目标，而不是默默做大范围外推。相机、焦距、分辨率/ISP裁切、基座坐标定义、标定平面高度改变后，应重新验证对应标定。

## 棋盘自动定位与四点入口

```sh
scara_geometry_tool inspect config/vision/inspect-auto.example.yml output.json
```

输出包括 JSON、带 90 点/编号的 `output.json.png`，以及 `output.json.rectified.png`。默认方向未确认，机器人 XY 无效。

自动流程为：自然边框轮廓与长线段产生候选 → 透视展开 → 提取两个方向的线段 → 拟合 9 列/10 行周期格网 → 用支持的内部线段交点重新估计单应性。河界断线和九宫斜线不作为完整主格线；棋盘外框仅作候选，不能把木框四角直接当棋盘四个交点。线缆连到外框时，使用长线段主方向和稳健范围补充候选，仍须通过内部格网支持度。

自动定位失败或结果不清楚时，使用 `inspect-manual.example.yml`。填入四个**最外侧格线交点**，按 `(0,0),(8,0),(8,9),(0,9)` 排列，核对后将 `canonical_order_confirmed` 设为 1。它是图像点输入接口，前端可以采用点击四点、修正自动角点或直接填写坐标；不要求机器人重新触碰四角。

规则格线具有 180° 对称性，不能单独可靠判断红黑端。不能用当前红黑棋子的分布代替棋盘朝向，因为棋子会过河。两种支持方式：

- 先看 90 点编号，再用 `manual_keep` / `manual_flip` 确认当前候选的端头；或使用有规范顺序的人工四角。
- 首次方向确认后，选棋盘印刷文字等非对称固定特征，生成模板。模板不选择棋子、手或可移动物体。

规范化图为 432×480，红方在显示图下方，交点 `(c,r)` 显示位置为 `(24+48*c,456-48*r)`。在该图内选择 `reference_patch: [x,y,w,h]`：

```sh
scara_geometry_tool reference oriented-inspect.yml orientation.yml
```

以后 `orientation: reference`、`orientation_reference: orientation.yml`，程序比较两个端头的印刷特征匹配，要求分数与领先差同时足够。被遮挡、对称或不明确时保留未判向状态，不输出目标。默认假设采集帧没有镜像；旋转可以处理，镜像须在采集/坐标恢复层明确撤销或改用已核对的人工四点。

## YOLO 对应到交点

`inspect` 的 `detections_file` 可读取现有 `host_preview.py` 的单帧 JSON 或 JSONL 最后一条记录。`frame_id` 必须与图像配置一致，不能拿旧检测套新棋盘。

- `coordinates: original`：原图坐标。
- `coordinates: roi`：已去 letterbox 的旋转后 ROI 坐标，兼容当前预览日志。程序先逆旋转，再加 ROI 偏移。
- `coordinates: network`：还在网络输入坐标，需要真实 `resized_size`、`padding`，不能只写一个不准确的缩放比例。

还原后只去畸变一次。检测中心转到网格坐标，按格距归一化距离归格，默认门限 0.35 格。一个交点对应多个框、偏格过远、类别非法、低置信度或帧不一致，均报无效，不强行补成一盘棋。未声明 `scene_clear` 的格点保持 unknown；empty 和 unknown 分别为 -1 和 -2。

检测框中心用于确定归属，**实际 XY 使用交点平面坐标**，不把棋子顶面中心直接投到基座当准确抓取位置。明显偏离交点的棋子和高度视差超出门限时须另行处理。未检出仍可能是模型漏检，稳定与清晰条件不能证明绝对空格。

`Stabilizer` 要求不同 frame_id 的连续一致结果，并检查四角位移。重复读取同一帧不累计；棋盘移动、冲突或不清晰会重置。调用方仍须检查图像新鲜度和拍摄/接收时间；CLI 是离线单帧工具，不宣称已完成在线时序验收。

## 给 IK / 取放的接口

```cpp
auto target = scara::gridTarget(plane, board, column, row, currentFrameId);
if (target) {
    // target->baseMm.x / y: 基座 TCP XY，mm
    // target->planeZmm: 标定平面高度，不是自动生成的抓取/抬升高度
    // target->calibrationId / frameId: 上层需要保持关联
}
```

只在标定通过、相机 ID 与数值配置一致、方向已确认、帧相符、交点在覆盖区内时返回有效结果。IK 的可达性、关节限位、TCP补偿、抓取高度、抬升路径和取放动作由运动层处理。当前 CMake 目标不链接任何电机或 CAN 实现，`inspect` 明确输出 `motion_enabled: 0`。
