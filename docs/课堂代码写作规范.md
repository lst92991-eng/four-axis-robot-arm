## 后续改代码按这几条

1. **先写一条完整的正常链路。** 入口只安排初始化、业务步骤和收尾。子函数只有在实际完成一项可命名的事时才成立。单纯转发、没有调用的空接口和遗留兼容分支查清调用方后删掉。
2. **数据在本段看得见。** 输入输出用普通值、数组、结构体和明确的引用参数。用单一的棋格、走法和动作表贯通本轮。需要说明失败时，用已有返回值或状态，异常留给 SDK、操作系统和外部接口的失败边界。对局退出按正常收尾处理。
3. **文件与协议在进入业务前处理。** 三点、Z 层和观察位由本机安装表直接填写。对局阶段接收像素、毫米、行列和关节角。文件读取属于相机、模型、引擎、标定或回放入口，UCI 字符串在引擎及棋谱边界转换。模块之间直接调用并交付数据。
4. **在决定下一步的位置检查。** 看得到的实际错误在对应入口检查，例如新帧无效、逆解不可达、驱动失联、落点待核对。一次有效输入沿同一路径传下去。保留实体机械臂的停稳、净空、参考与结果确认。
5. **注释说明下一步依赖什么。** 写单位、坐标方向、算法中容易误用的量，以及动作和资源收尾的先后理由。行内代码已经把意思写明时直接读代码。删除废弃方案、测试打印和复述函数名的注释。
6. **用同一套代码验收。** `tests/` 提供替身和场景，`bench/` 提供夹具、示教与诊断。用生产调用路径的输入和输出比较前后效果。真机教程从实际入口开始，不把仿真运行脚本作为对局模块。

以 `4bf40f8` 为改前对照。已经按文件顺序排列的主线仍经终端或台架抛出正常退出异常。根构建在测试开关之外编译旧 JSON 读表器和仿真入口。原生文字对局还生成一份没有显示端读取的双画面。用退出流程、实际构建目标和图像消费方核查这三处。

原生 RKNN 构建默认关闭 `BUILD_TESTING`。台架和离线回归通过各自的入口选入示教、旧配置兼容和仿真。原生对局使用检测结果，独立视觉预览与 Windows 台架各在自己的入口绘图。

教师参考的程序已经从采样一路调用到外设动作。机械臂目前走通的是 Windows 台架路径。原生 Linux 的四个 `Drive_*` 接入点仍待实现，课堂讲原生入口时要把这个边界讲清楚。器件断开、操作员停机和落子未确认由实际运行结果决定，各有清楚的出口。[板端驱动入口](../app/rv1106.cpp) · [实机台架入口](../bench/README.md)

每次改动完，从实际入口顺读一遍普通走子、吃子和退出。使用相同样本核对格点、检测和动作。有效行数作为对照记录，代码能直接手写复现才算完成。
