# 完整对弈主程序与执行器接口

2026-11-14已补齐 `app/game_main.cpp`：同一主循环连接初始化、观察、玩家走法确认、Pikafish、取放计划、执行回执、落子复核、下一回合和结束。`scara_game_sim`使用明确场景夹具运行同一main/业务代码；`scara_game`连接真实相机/NPU/Pikafish，并通过执行接口交给后续SPI-CAN/H桥程序。未调用实际电机或磁铁。

## 运行顺序

1. `Match_load`读取固定布局、已有机械参考、示教Z、观察位与吃子区。完整对局启动前核对90格可映射且逆解可达，不添加机械碰限位或新的角度软限位。
2. 终端回车确认空吸头已抬离棋盘、手已移开，发送prepare：保持吸持语义、进入示教搬运Z、进入示教观察位。执行器必须确认机械参考有效、动作完成并停稳后回应。
3. 相机读取三个不同有效帧，展示识别结果；操作者确认后重新取图，盘面一致才建立初始Game。标准局或残局均可，行棋方由配置指定。
4. 每回合先查询已确认局面的合法走法。人类回合在走完且手移开后按回车，由新观察识别唯一合法变化；机器人回合由引擎选择应手，搜索结束后再观察盘面，确认没有变化才生成动作。
5. 机器人完成取放后抬到搬运高度并回观察位，避免小臂挡住棋盘。收到同编号、明确停稳的执行结果后重新取三帧；实际盘面吻合才写入完整历史。
6. 无合法走法结束；复杂重复局面标为review_required并停止等待人工裁定，不冒称自动判和。思考和运动时关闭相机/NPU，避免与引擎同时占用板端资源。

## 需要真实示教的配置

配置模板为 `config/game.example.json`，null必须换成真实数值；不要把仿真夹具当现场坐标。各路径相对配置文件解析。

| 配置 | 含义 |
| --- | --- |
| layout_file | 已确认四角与plane_file的固定布局 |
| arm_file / heights_file | 现有机械参考与J1吸取/搬运高度文件 |
| park_joints_deg | 两个数：J2反馈角、J3电机角，单位度；应为抬升后能看清整张棋盘的观察姿态 |
| capture_place_mm | 吃子区基座XY，单位毫米，必须可达 |
| human_red / red_to_move | 人类是否执红、开局是否红方行棋 |
| think_ms | 引擎思考毫秒数 |
| camera_url / label_image / engine_directory | 原RTSP地址、随程序字图、原Pikafish目录 |
| work_directory | 状态、预览、动作请求与回执所在目录 |

J1仍用示教的绝对驱动角度；未猜丝杆导程。J2/J3单位沿用现有模型和反馈，不把减速器换算重复做一遍。J4保持原姿态。XY速度/加减速和控制器到位判断由执行层采用自己的已验证配置，主程序不把等待时间当作到位。

## 文件执行接口

主程序原子发布 `work_directory/motion-request.json`。同一时刻只有一个未确认请求，ticket在本次运行内唯一。示例字段如下，数值只说明格式：

```json
{
  "ticket": "运行编号-请求序号",
  "simulated": 0,
  "purpose": "move",
  "move": "a3a4",
  "steps": [
    {"action": "hold"},
    {"action": "xy", "j2_deg": 12.5, "j3_motor_deg": -36.0},
    {"action": "z", "j1_deg": -20000.0, "speed_deg_s": 180.0},
    {"action": "release", "duration_ms": 20}
  ]
}
```

实际请求包含完整步骤，此片段不是可直接执行的取放轨迹。`purpose=prepare`为进入示教工作高度/观察位；`purpose=move`为完整搬子，吃子时先搬走目标棋子再搬自己的棋子，最后回观察位。

`hold`、`release`是吸持/释放语义，不是某引脚高低电平。H桥如何实现极性、电流和脉冲由你的执行器负责；release完成后才能执行下一条抬升。执行器按数组顺序逐步执行、确认到位，并对ticket去重；请求文件保留不代表可以再次执行。真实执行器必须拒绝simulated=1。

全部动作完成并停稳、吸头已让开棋盘后，执行器先写临时文件，再原子替换 `motion-reply.json`：

```json
{"ticket":"同一请求编号","settled":1,"success":1}
```

失败时先停止并稳定机构，再回应 `success:0`，可附 `error`字符串。尚在运动时可以没有回执或settled=0。主程序忽略其他编号及未停稳回执，绝不因仅发送成功就提交走法。success必须是0或1。

Ctrl+C或异常退出时，对未确认请求发布 `motion-cancel.json`：

```json
{"ticket":"正在执行的编号","action":"stop"}
```

这是停止请求，不是已经停稳的证明。执行器负责及时响应、真实状态反馈、CAN心跳/实时监督和急停。当前程序不直接实现SPI-CAN或H桥驱动。若你希望直接链接驱动库，也可替换 `IO_execute` 内部调用；保持“返回时已停稳、success表示全部步骤完成”的契约即可，棋局主循环不变。

## 操作与恢复

- 玩家每次走完、手移开后在终端回车。没有发生唯一合法变化时保留原棋局，允许调整后重读。
- `retry`或回车：只重新观察，不重新发动作。失败回执不会因此自动变成成功。
- `accept`：操作员确认实际动作已经完成且机构停在观察位；仍须新盘面与expected一致才提交。
- `restored`：确认棋子全部复位、吸头空且回观察位；新观察必须等于上一步权威盘面，才清除pending并重新规划。完整历史不清空。
- `resign`认输，`draw`同意和棋。机械动作未确认时先处理恢复，不能跳过它直接结束。
- `quit`或Ctrl+C退出。status.json保留已完成历史与待确认状态，当前不提供进程重启后自动续局。

不能把一次执行失败后的请求盲目重发。主程序恢复流程只在人工明确确认后重新规划，不自动清故障、假定零位或重复吸放。

# 固定棋盘的视觉、棋局与取放接口

当前是2026-11-13固定流程精简版。完整C++共1800有效行；主要入口和逐文件行数见[README](../README.md)。旧接入记录留在文末，其中类方法、动态棋盘与外部FEN解析的旧接口不代表当前代码。

## 初始化一次

- `loadPlane(path, map)`：读取新采点或保存的标定，复算映射并核对独立采点误差；相机必须匹配固定的1280×720原图配置。
- `boardFromCorners(corners, confirmed, grid)`：四角按红方视角a0、i0、i9、a9给出，确认方向后生成90个交点。
- `FixedBoard_setup(map, grid, session.layout)`：缓存90个基座XY。失败时不保留上一次坐标。
- `Arm_load`与`WorkHeights_load`：读取已保存的机械参考和实际示教Z；没有新标定或猜测丝杆导程。
- `Game_reset(game, board, redToMove, humanRed)`：从标准初局或已确认的任意盘面开始，生成起始FEN并清空历史。

只移动棋盘时重新设置四角即可；相机/基座相对位置或焦距改变时重新标定映射。修改布局后调用 `session.stable.reset()`，保留棋局历史，再获取新的稳定观测。当前不自动找格线或判断旋转朝向。

## 每回合的数据顺序

| 调用 | 输入 | 输出或状态变化 |
| --- | --- | --- |
| `Session_observe` | 新帧编号、YOLO原图检测、画面是否无遮挡 | 将身份分配到交点，三个不同有效帧一致后得到有效棋局观察 |
| `Pikafish::legalMoves(game, legal)` | 已确认Game | 引擎当前合法走法；必须先确认调用成功 |
| `Session_acceptHuman` | 稳定观察和合法走法表 | 唯一匹配的人类走法，更新已完成历史 |
| `Pikafish::think(game, timeMs, choice)` | 起始FEN与完整历史所在的Game、思考毫秒数 | 引擎应手 |
| `Session_plan` | 应手及当前合法走法表 | 查固定XY、逆解、生成取放步骤，全部就绪后保存pending |
| `Session_confirm` | 动作是否成功、已更新的稳定观察 | 新盘面等于预期才提交走法和历史；否则保留待确认状态 |

格点层和棋局层的观察都只有一个valid标志，分别表示该阶段的结果是否可用。固定XY查表与帧号无关；帧号留在识别观察里，用于拒绝重复证据。YOLO置信度仍用于0.50阈值与画框，未再复制到无消费者的格点数组。

视觉行0在红方底线，棋局数组行0在黑方底线，转换是 `chessRow = 9 - visionRow`。UCI的 `a3a4` 对应视觉 `(0,3)→(0,4)`。转换函数chessObservation就在session.cpp中，已经没有独立vision_bridge层。

Pikafish只接收由Game维护的状态，直接发送 `game.baseFen` 和 `game.history`；不再把自己的FEN反向解析一遍。FEN输出仍保留全部字段，任意初始盘面通过Game_reset设置，外部FEN文本导入不在精简版中。引擎响应的计数、格式、重复走法、部分I/O、超时、取消及回收检查保留；选中走法仍须属于合法列表。

## 取放与结束

执行前处于已示教的搬运高度，J4保持原姿态。普通取放为：保持吸持 → 源XY → 吸取Z → 搬运Z → 目标XY → 释放Z → 释放脉冲 → 搬运Z。脉冲结束后才抬升。当前是被动吸持/通电脉冲释放，H桥仍待接入。

吃子先把目标棋子搬到已示教的吃子区，再搬自己的棋子。未示教吃子区时不生成该计划。`Game_finish(game, Result::Draw/RedWon/BlackWon)`统一同意和棋与认输，正在搬子时不能结束。没有合法走法时当前方负；复杂重复局面仍转人工裁定，没有声称实现完整长将/长捉裁判。

C++模块只生成步骤，没有连接正式SPI-CAN执行端。现有Python上位机与演示保留。当前通过14组CTest和60项Python检查；UCI使用真实实现加POSIX替身，模型使用保存张量与原ONNX离线对照。真实Linux引擎、ARM构建、NPU及整机动作仍待验证。
