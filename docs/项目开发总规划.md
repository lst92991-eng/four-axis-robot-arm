### 1.2 电磁铁与33mm棋具的选型条件

“33mm、通用外观”不等于“能被电磁铁吸起”。后续棋具需要有可被吸附的材料/结构，或经过明确的可吸附改造；普通木质/塑料本体不能默认适用。尺寸、外观与可吸附性分别验收。

25mm棋子有磁铁，也仍要测试从棋子顶面吸取、克服棋盘吸持、运输和释放。永久磁铁/残磁可能影响断电释放，不能把线圈通电当作已经抓住棋子，也不能把断电指令当作棋子已经落下。

## 2. 模块划分：六个职责块

这是职责边界，不要求现在创建六套目录、类或测试程序。按阶段增加普通函数和少量必要文件。

| 模块 | 负责 | 输出给谁 | 单独验收的结果 |
|---|---|---|---|
| 设备接口 | USB-CAN传输、X42S协议、四轴状态/反馈、停止、电磁铁开关 | 运动与取放 | 指令、应答和真实状态能对应；故障有界退出 |
| 运动 | 单位/零位、FK/IK、轨迹与同步、已验证的限位/路径、运动EKF | 取放 | 给定目标在当前机械版本上正确运动并反馈状态 |
| 取放执行 | 到源点、吸取、抬升、搬运、释放、吃子及收纳 | 主流程 | 一次明确的搬子任务成功，或明确停在可复核的失败状态 |
| 视觉 | NV12转换、棋盘/标记定位、标定、NPU识别、90格状态与可信性 | 主流程/运动观测 | 输出有时间戳、坐标定义和不确定标记的观测 |
| 棋局与引擎 | 盘面差分、合法走法、历史、Pikafish请求、结果判断 | 主流程 | 合法走法与已提交棋局；不以通信错误代替终局 |
| 主流程 | 人机轮次、调用顺序、停止与恢复、显示必要结果 | 用户 | 一个能按执行顺序讲清楚的完整对局入口 |

程序读取一份当前有效参数；旧/新结构及25/30棋具的快照随阶段保存。候选新CAD参数不自动替换现用旧机运行参数。机械臂版本改变不另写一套FK/IK，棋子改变不另写一套棋局。视觉教学入口仍按单文件执行顺序展开，RKNN和硬件协议细节留在各自明确的边界。

模块间只约定必要数据：棋局用10×9交点与双方14类身份，走法用起终交点；标定把交点映射为TCP位置；运动内部位置用mm、旋转关节用rad；电机协议单位只在设备边界转换。图像像素、棋盘行列、基座坐标及工具坐标各有明确来源，不在不同模块重复猜换算关系。

### 2.1 已获用户初步认可的视觉分工

```text
MIPI NV12 → OpenCV转BGR → ArUco定位 → 透视矫正/裁剪/RGB与尺寸准备
→ RV1106 NPU运行YOLOv5识别红黑14类 → 程序映射90交点
```

## 3. 开发顺序与检验点

**前置：规划审核→用户授权现状归档→本地与远程归档均核对成功→按清单整理旧代码→开始阶段1。** 本轮未执行这一归档/清理步骤；已经做过的虚拟软件、模型和CAD证据均先保留。

下面每阶段均经过“实现→实测→用户认可效果→教学精简→回归→用户审核代码并授权提交→本地/远程归档成功”的关口。表内检验点不能由虚拟结果替代实机结果。

| 阶段 | 本阶段完成什么 | 检验点/进入下一阶段的条件 |
|---|---|---|
| 1 RV1106通信与单轴基础运动 | 确认USB-CAN在本板Linux上的真实通信路径；读取驱动状态；单轴小范围正反转、停止、超时 | 型号/固件/节点与协议对应；方向与运动量正确；无盲重发；用户认可基础运动效果。电脑厂家上位机能动不等于RV端已通 |
| 2 四轴反馈、单位与回零 | J1/J2/Z/R对应表、方向、传动换算、回零、停止/限位、掉线恢复 | 各轴不串号；反馈可用且单位正确；回零可重复；Z保持行为明确；重新连接不自动续跑旧指令 |
| 3 电磁铁静态吸放 | 确认额定电压/电流、驱动接口、线圈保护和允许通电时间，测试25mm实物棋子顶吸和释放 | 单子能吸起且能放下；不连带邻子；吸持/释放等待与温升限制有依据；停止/断电时带子状态可解释。先不结合复杂路径 |
| 4 平滑运动与同步 | 利用驱动已有功能，补最小速度/加速度及必要jerk规划，协调多轴完成同一段运动 | 起步、换向和停止达到用户认可的顺滑程度；不让每个路径采样点零速起停；反馈与到位判定有效 |
| 5 FK/IK与当前机型点位 | 接入当前机械参数、TCP、零偏；检查点位、连续路径、同一肘型与实际障碍 | 独立点位核验坐标和误差；奇异位形/碰撞/限位得到处理；旧机只使用已验证区域；CAD采样图不是连续运动认证 |
| 6 指定点位取放与吃子 | 不依赖识别和引擎，按给定源/目标完成吸取、抬升、搬运、释放；吃子先清目标，再搬己子 | 普通搬子、吃子、收纳、漏吸/未释放和途中停止可复核；工具、棋子实体、完整路径纳入检查。20mm抬升只是此前计算方案，验证后才能用于动作 |
| 7 相机机位、棋盘定位与标定 | 在临时可调机位测试真实棋盘/标记范围、画质与遮挡；再定省料支架和棋盘到基座标定 | 全盘及四角白边完整；远近端文字清晰；机位/棋盘/取放高度定义一致；停车稳定时间有记录。此时才确定支架打印尺寸 |
| 8 运动EKF | 用真实编码器反馈及可校准的末端观测，估计运动状态并接入监督/必要反馈修正 | 状态、模型、噪声、时间戳和延迟明确；有同工况原始反馈/估计/独立观测对比；不用滤波掩盖传动比、回零、背隙或松动 |
| 9 当前棋具YOLO识别 | 真板输出红黑14类及空格；此时若仍用25mm先验证该套，33mm已到位可直接作为识别基准；按实拍决定沿用权重、微调或替换 | 数据来源/划分/权重可追溯；独立实拍包含各类、远角、满盘、残局和遮挡；低置信/重复检测不进入动作；新字体不能只靠缩放增强宣称适配 |
| 10 棋局、引擎与单回合闭环 | 合法性、历史和结果处理；把已验证的识别与取放接成一个人机回合 | 人的非法走法不改历史；机器走法先核验合法且可执行，实物复拍正确后才提交；中断后盘面和引擎历史一致。旧机可用限定场景验证，不强求全盘 |
| U 新结构与33mm升级复验 | 新机到位后先沿用25mm棋子验证机械变化；再换33mm棋具验证吸附、定位、识别与布局 | 按第4节复验；没有通过的相关阶段退回重做。完成正式全盘联调前必须通过，不要求先完成旧机整盘版本 |
| F 正式全盘联调与教学复现 | 在最终机型和33mm可吸附棋具上验证90点、吃子区、整局、异常恢复和从干净环境复现 | 整盘与完整取放路径通过；整局和异常场景有记录；用户认可效果并审核最小代码；授权最终归档后交付 |

### 3.1 阶段1接入讨论（2026-10-10）

用户已确认转接工具为ZDT_CANable V1.0。建议按四个小检验点推进：

1. **电脑识别工具。** 先只接USB端到Windows电脑，核对设备枚举和当前工具固件；此时无需连接电机。
2. **电脑验证单节点。** 按驱动手册核对接线、外部供电、终端、电机地址、CAN速率与校验，用厂家上位机只读取版本/状态，确认真实驱动应答。
3. **RV1106只读收发。** 工具移到板子的USB Host口，核对本板驱动/内核路径，用单文件C++实现一条查询、接收解析和超时。达到这里才证明板端CAN链路已通。
4. **单轴基础运动。** 在既定授权、范围和停止方式下加入低速短行程正反转与停止；用户认可效果后再精简、回归和审核提交。

最终运行链路为`RV1106 USB Host→ZDT_CANable→CAN总线→电机驱动`；电脑先验证只为排查基础链路。CANable固件（如candleLight/slcan）和电机驱动固件（X/Emm）是独立项目。

[厂家工具说明](https://blog.csdn.net/zhangdatou666/article/details/132269560)注明V1.0出厂默认candleLight、配套cangaroo；用户手中固件仍以识别为准。当前处于商讨与资料核对，没有操作电机、改固件或创建新的运动程序。

2026-10-10检查进展：用户已插入工具，未连接CAN总线。Windows最终枚举为`1D50:606F`、`candleLight USB to CAN adapter`，通讯接口MI_00绑定WinUSB、问题码0。**只通过第1个USB识别检验点**，尚未验证CAN收发或电机应答。首查曾显示VMware接管，复查已由Windows主机正常枚举；本次没有主动切换USB、改驱动或刷固件。证据见[USB识别记录](../output/hardware-validation/stage1-usb-identification.json)。

新结构若提前到位，U可以在受影响阶段开始前插入，不必先把旧版阶段重复做到底。机械加工等待期间可先完成阶段1～6中满足输入条件的工作；视觉/引擎已有材料可以离线整理，但不自动越过用户的阶段授权和审核关口。

旧机若遇到合法但不可达的走法，应停止自动执行并明确说明；不能删除这些合法走法或裁掉棋盘，假装已经支持整盘。

## 5. 运动EKF的最小教学方案

优先从平面两关节做4状态示例：`x=[q1,q2,dq1,dq2]`。编码器提供关节反馈，固定相机对末端标记提供经过标定的XY观测，XY观测函数由真实FK形成非线性；Z/R先沿各自真实反馈处理，不为凑算法名称扩大状态。

这是待对应阶段验证的方案，不是已完成的反馈控制。只有编码器和线性模型时如实称KF；若末端观测在运动中不可用、时间/坐标不能对齐，先保留待验收项。离线回放和虚拟执行器可以验证数学实现，不能代替真机运动观测。

轨迹平顺主要由速度/加速度规划与驱动环实现。EKF估计不能直接消除机械背隙或支架松动，也不把普通Linux用户态和USB-CAN当作未经验证的硬实时电流/速度环。

## 6. 完整对局与故障处理

主流程保持一条可读路径：

```text
等待人走 → 停稳取图 → 可信盘面差分 → 合法性核验 → 提交人的走法
→ 皮卡鱼应手 → 合法性/当前机型可执行性核验 → 清目标/搬己子
→ 机械臂停车 → 复拍核对 → 提交机器走法 → 等待人走
```

不确定盘面、手部遮挡、引擎异常、反馈超时、吸放失败或复拍不一致均停止推进棋局。机器的“计划走法”和“已完成走法”分开；通电、发指令或到位应答不足以证明棋子搬运成功。吸附确认可优先结合视觉复核；若证据不足需停下核对，不为省代码直接假定成功。

人的非法走法提示还原，复拍与已提交盘面一致后再继续。吃子中断须保留当前走法和已执行步骤，再按现场复核处理，不能从头盲重跑清目标/搬己子两段任务。

### 10.7 C1用户定案（2026-10-14）

用户确认原文：“这版我已经可以接受了”。批准范围为以下完整CAN构造方法：保留接口名参数，使用if_nametoindex；无名称判空/长度检查、require或try/catch；各系统操作分别判断失败，绑定/错误订阅失败关闭句柄并抛出异常。此结论覆盖10.5及10.6中C1的待定草案，不代表其他方法或全项目错误处理已批准。

```cpp
Can::Can(const char* interface)
{
    // 根据名称取得CAN接口编号。
    unsigned index = if_nametoindex(interface);
    if (index == 0)
        throw std::runtime_error("CAN接口不存在");

    // 创建非阻塞CAN通信句柄。
    fd_ = socket(PF_CAN, SOCK_RAW | SOCK_NONBLOCK, CAN_RAW);
    if (fd_ < 0)
        throw std::runtime_error("创建CAN连接失败");

    // 绑定到指定CAN接口。
    sockaddr_can address{};
    address.can_family = AF_CAN;
    address.can_ifindex = index;

    if (bind(fd_, reinterpret_cast<sockaddr*>(&address),
             sizeof(address)) < 0) {
        close(fd_);
        throw std::runtime_error("CAN绑定失败");
    }

    // 允许接收CAN总线错误信息。
    can_err_mask_t errors = CAN_ERR_MASK;

    if (setsockopt(fd_, SOL_CAN_RAW, CAN_RAW_ERR_FILTER,
                   &errors, sizeof(errors)) < 0) {
        close(fd_);
        throw std::runtime_error("CAN错误订阅失败");
    }
}
```

状态：设计已定案、尚未实施。按当前模块方法商定后统一修改的约定，源码暂留原版本。下一项C2析构建议保持单次close(fd_)，不增加显式close入口或状态分支；待用户审议。
