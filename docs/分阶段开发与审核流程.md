# 分阶段开发与审核流程

日期：2026-10-09。适用于本项目后续真实机械臂接入与教学代码整理。

2026-10-13更新：Z轴已按用户授权完成实物基础运动与恒速测试，CAN/Motor已有待审核的C++候选实现。当前转入剩余工作盘点与逐模块最小设计商讨；不再沿用“尚未真实电机运动”的旧时态。完成度与待办统一见[项目开发总规划第10节](项目开发总规划.md#10-距离项目结束的待办与最小实现商讨2026-10-13)。未授权提交、推送或旧代码清理。

2026-10-14最新覆盖规则（教学分支）：用户明确选择从空白开始，第一次提交需求与技术栈文档，第二次起每确认一个接口就实现、验证并本地提交，提交正文详述设计理由。不再等整个模块才实施，也不重复索取已授权的单接口本地提交。该规则仅改变本教学分支的实施/本地提交粒度；未讨论接口、实物效果、最终代码验收和远程推送仍分别处理。分支与提交结果见总规划10.8。

## 1. 每阶段都经过同一组审核关口

```text
确认本阶段输入与范围 → 用户确认本模块最小设计 → 实现最小可运行功能 → 实测并展示结果
→ 用户确认运动/功能效果可接受 → 精简为教学实现 → 回归验证
→ 用户审核代码 → 用户授权本阶段本地提交与远程推送
→ 核对本地及远程提交结果 → 才进入下一阶段
```

| 关口 | 要交给用户看的内容 | 通过条件 |
|---|---|---|
| 范围确认 | 本阶段输入、一个明确目标、拟改文件及代码增量估计 | 参数足以支持本阶段动作；范围已经得到授权 |
| 最小设计商讨 | 必要功能、复用/删减项、头文件草案、调用顺序、失败职责、文件/行数预算及验收方式 | 用户确认本次设计后再修改模块；不把“代码已短”当作已获认可 |
| 功能实测 | 可复现的操作、实物现象或视频、必要测量、失败与停止结果 | 工程检查通过，并由用户明确确认效果可接受 |
| 教学精简 | 删除临时分支、重复代码和多余日志后的代码差异、文件职责、行数变化 | 保留已接受行为和必要保护，代码按执行顺序容易讲清楚 |
| 精简回归 | 同一组关键动作与异常检查的前后结果 | 精简没有改变运动效果、单位、停止或故障处理；若效果变化，重新取得用户确认 |
| 代码审核 | 本阶段完整有效代码、修改说明和回归记录 | 用户确认代码通过；若提出修改，完成修改并重新提交涉及的部分供审核 |
| 提交归档 | 准备提交的文件清单、差异、提交说明、远端与分支 | 用户明确授权 commit 与 push；成功后记录本地提交号和远端对应提交号 |

用户可在同一条消息中完成“代码通过，允许提交并推送”的授权，不要求重复确认已授权事项。“运动看起来不错”只通过效果关口，不自动授权提交；未收到回复不能视为通过。推送失败时保留当前阶段并说明原因，不能按已归档继续下一阶段。

调试中可以反复修正本阶段问题，但不得借修正引入下一阶段功能。后续阶段只允许已授权的资料阅读、参数整理和离线分析准备；这些准备不能替代审核、提前接入生产流程或启动设备。用户明确改变顺序或范围时，先更新本表中的依赖与验收要求。

2026-10-14细化：模块最小设计按方法逐项商讨。每次明确一个方法的职责、参数返回、保留/删除/迁移、拟写法和失败处理，记录用户结论。当前模块相关方法定案后先汇总头文件与调用顺序，再实施已确认范围。方法决策只维护总规划第10.5节，不在本流程重复抄表；保存实现事实不等于用户已批准现有设计或源码冻结。

## 2. 接入前：先归档，再清理

此步骤等机械臂接入、用户明确授权“先归档，再清理”后执行。本轮不执行。

2026-10-09本次规划期间只读复核：工作区尚无HEAD提交，`git remote -v`为空。开始归档时仍须再次核对，并使用用户指定的远端；本轮没有创建仓库、提交或推送。

1. **先核对 Git 现状。** 主线程检查当前分支、HEAD、未提交/未跟踪文件和远端配置，记录实际结果。“当前没有 commit / remote”需在执行时复核，不能仅凭旧对话写成已确认事实。若确实没有提交，归档是首次提交；若没有远端，先取得用户指定的仓库地址、分支及访问条件，不自行创建公开仓库。
2. **整理完整归档清单。** 保存现有自有代码、测试、构建/运行入口、需求与参数、必要配置，以及模型/引擎/依赖的来源、版本、许可证与运行证据。大模型、库和原始机械资料若不适合直接纳入 Git，记录独立归档位置和 SHA-256，并确认可取回。构建缓存、临时日志、个人路径和凭据不进入提交；不能误把运行必需输入当缓存丢弃。
3. **按授权提交并推送现状。** 检查提交包含预定文件，远端分支确实指向同一提交；另存资产也已归档可取回。两处均完成后才清理，不以“push 命令已经运行”代替结果核对。
4. **按已授权清单清理工作区。** 清理清单先列明保留、移出和删除项及恢复来源。保留当前中国象棋需求、必要参数及证据、机械/坐标结构说明、已批准的支架打印件及源文件、本流程和项目约定；第一阶段需要的最小目录与构建入口按实际需要建立。旧视觉、棋局、虚拟执行器、训练和演示代码以归档为恢复来源，不默认继续留在新的生产入口里。外部原始 CAD、BOM、压缩包和用户文件不在旧代码清理范围内。
5. **展示清理结果。** 给出前后目录、保留信息及对应归档位置。第一阶段从这份清晰的工作区开始；清理不扩大为磁盘全局删除，也不删除远端历史。

阶段提交是可追溯存档，**不自动宣布代码冻结**。若用户以后要求冻结，由用户指定版本和有效文件范围，再保存相应清单；不能静默用当前 HEAD 代替用户指定基准。

## 3. 开发节点及依赖顺序

阶段清单、模块边界和具体检验点只维护在[项目开发总规划第3节](项目开发总规划.md#3-开发顺序与检验点)，本文件不再保留另一套节点表。旧流程中的吸盘/气路已由用户明确的电磁铁末端替代；旧机、25mm磁性棋具与新版/33mm升级分别验收。

每阶段均完整经过第1节关口。已有历史实现可以作为参考，不直接算作新硬件阶段验收通过。新结构到位时按总规划的U阶段插入复验，最终全盘验收不要求先把旧机做成完整版本。

第一阶段保留本轴必要的停止、超时和行程保护。未回零时不能宣称绝对坐标已建立；受限调试运动依据已确认的驱动模式和现场条件决定。不能用未经验证的FK/IK替代单位核对，也不能靠滤波掩盖安装或传动误差。

非运动节点由用户确认图像、识别或棋局行为；精简、回归、代码审核和提交推送关口仍保留。缺少资料或反馈时列明缺项，不用虚拟结果替代实机验收，不自动跳到后续节点。

## 4. 精简的边界与每阶段记录

精简保留：清楚的执行顺序、中文意图注释、正确单位、限位与停止、超时、真实反馈和失败恢复。优先移除：本阶段不用的入口、临时测试分支、重复状态/参数、过多日志、只有一个实现的通用封装。测试沿用一个入口，临时诊断不混入正式操作流程。

每阶段只留一份简短记录，随该阶段提交保存：

```text
阶段/日期：
输入硬件、固件、参数来源及当前限制：
本阶段文件与范围；预计代码增量：
实测操作、结果、异常/停止检查、视频或数据位置：
用户运动/功能确认原文或消息日期：
精简内容；前后物理行/非空行（含注释，排除第三方、测试和生成物）：
精简后的关键回归结果：
用户代码审核结果及提交/推送授权：
本地提交号；远端与分支；核对的远端提交号：
遗留问题；下一阶段是否允许开始：
```

详细参数统一引用[机械臂软件参数与运动控制说明](机械臂软件参数与运动控制说明.md)及总规划中的最新用户输入，避免重复维护数值。当前本轮只更新待办与商讨流程；先前Z轴运动授权和证据保留，后续各模块按对应范围和检验点执行。
