# 参考系标定与下棋闭环：最短落地路线

依据用户2026-11-09技术栈截图：`docs/hardware/stack-user-20261109.png`。正式主程序沿用C++17、OpenCV5.0.0、Pikafish 2023-03-05及配套NNUE、UCI、起始FEN与完整已完成走法历史、CMake和RV1106 ARM交叉工具链。使用现有YOLO，不训练、不替换已验证预处理，不使用ArUco。

目标先收敛到“指定两点搬一枚棋子→吃一枚棋子→人走一手、机器应一手”，再扩展完整对局。现有Windows/Python手动工具用于电机调试，不冒充已部署的C++整机应用。暂不把500°/s极限、自动回零、复杂路径优化或全自动裁判作为第一手棋的前置目标。

## 1. 先接上真实机械参考

用户将提供SolidWorks总装及引用零件，或完整STEP总装。提取J2/J3轴心距、J3到工具轴的长度、TCP偏置、传动关系与轴正方向；图纸未明确给出的丝杆导程、当前装配差异和机械零点保留待确认，不能从文件名或渲染图猜数值。

J1已有电角标定和手动运动；J2～J4当前实板仍未配置有效电角零点。先将J2/J3电角标定和用户已有机械参考衔接，低速核对方向、传动比与FK，随后再取像素标定点。J4是否可固定使用取决于吸头是否与旋转轴同心及实际TCP偏置，不能凭圆形棋子就忽略偏置。

Z记录丝杆导程、吸头接触棋面的位置、抬升净空和工作行程。当前负数多圈临时参考只供调试；自动取放前建立正式Z参考，并设置实测自动行程，不能因手动模式无固定终点就取消自动模式边界。

## 2. 一次完成像素与基座XY标定

固定相机、焦点、图像几何和棋盘平面高度；选可达且分散的6个拟合点＋3个独立检查点，不要求触碰棋盘四角。记录原始图像像素与可靠TCP基座毫米坐标，用现有工具计算并保存`PlaneMap`。独立点误差满足按棋子/吸头余量确定的毫米阈值后，才视为可用。

接触点必须对应棋盘平面，不用棋子顶面的YOLO框中心代替标定平面点。若使用未去畸变原图近似，独立验证必须覆盖工作区域；基座坐标必须来自已核对的FK或独立测量，不能由待求映射自己反算后再当作真值。

棋盘平移/旋转后，仅重新识别格线并确认红黑朝向；必要时人工确认四个最外侧格线交点。保持固定显示视野，定位失败不复用旧交点。棋盘移出标定覆盖范围时需扩充验证，不能无约束外推。

## 3. 用完整搬子验证执行链

先一枚棋子：指定源/目标交点→两处基座XY→IK可达及路径检查→抬升→移到源点→下降吸子→抬升→移到目标→下降释放→抬升→复拍确认。分别保存源点、目标点、接触Z、安全Z和磁铁吸放结果。

下一步验证吃子：先把目标棋子移到已标定的吃子区，再搬本方棋子。供电/通信/机械动作失败时不继续后续步骤，记录实际完成到哪一步。驱动ACK或磁铁通电不算棋子搬运成功，只有新鲜视觉确认或明确人工确认才提交执行结果。

最早的自动动作先限定已验证区域与中低速；J1角速度换算毫米速度必须使用真实导程。其他轴的扭矩、方向、限位与传动映射不能照抄J1。

## 4. 按用户技术栈连接对弈

- C++棋局管理保存9×10权威盘面、红黑轮次、起始FEN和完整已完成走法历史。计划动作与已完成动作分开；执行/复拍失败不把计划走法写入历史。
- Pikafish固定2023-03-05及配套**预解压**NNUE，核对哈希；使用`position fen ... moves ...`传递完整上下文，`go movetime`控制思考时间，接收并验证`bestmove`。合法走法查询复用该版本已验证的`go perft 1`扩展，不将其当成所有UCI引擎都支持的通用命令。
- 第一版由用户确认人类落子完成，再从稳定视觉变化推断一步合法棋；检测有遮挡、unknown或重复占格时等待确认，不强行补盘。
- 历史棋局模块`row=0`为黑方底线，当前视觉`row=0`为红方底线，接入时明确转换`chessRow=9-visionRow`，列不变，并用开局/吃子/旋转棋盘检查，不能直接复制数组。
- UCI进程调用有超时和取消，CAN心跳监督独立运行；引擎搜索不能阻塞500ms通信看门狗。历史引擎约90MiB常驻，当前YOLO/相机同时运行的内存与响应需实板检查。
- 三次重复或复杂长将追逐先转人工裁定，不将简化状态机宣称为完整竞赛裁判。

## 下一次现场顺序

先读用户提供的总装，确认尺寸与传动；随后接通J2/J3的电角和机械参考、测Z接触/抬升高度；再采6＋3点标定。第一项实物交付是“选两个交点，完整搬一枚棋子并核对落点”。这些现场数据齐备前，软件可先完成棋局、UCI、坐标适配及模拟执行检查，不擅自启动整机自动运动。
